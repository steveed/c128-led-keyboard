# Rev 3 keyboard firmware

ESP-IDF project for the ESP32-S3.  What is here today covers milestones 1 to 3 of the plan:
scan the physical matrix, mirror it into the CH446Q crosspoint so the C128 sees the keys, the
three lock keys as saved toggles, RESTORE sense and press, the LED engine (patterns, key
actions, lock indicators, a current cap), and a console that prints key names and takes
commands.  The rest of the feature list (command layer, macros, WiFi, USB keyboard mode,
network keyboard) builds on this.

## Development setup (macOS)

Nothing installs on the host except Docker Desktop and, for flashing, a Python venv with
`esptool` that the Makefile creates itself.

1. Install Docker Desktop and start it.
2. From this directory: `make build`.  The first run pulls Espressif's `espressif/idf`
   image (about 2 GB) and compiles; later builds take under a minute thanks to the ccache
   volume.  The build writes `build/c128kb.bin`.
3. Plug the DevKitC-1 in by its **USB** port (the one labeled USB, not UART).  It shows up
   as `/dev/cu.usbmodem*`.  `make flash` writes the bootloader, partition table and app.
   If the board does not enter download mode by itself, hold BOOT, tap RESET, release BOOT,
   then flash.
4. `make monitor` opens the console (screen, 115200; quit with ctrl-a then k).  Press `?`.

`make build` is the bench rig (a devkit scanning the rev 2.3 board).  `make build-rev3`
builds for the rev 3 board into `build-rev3/`; flash it with the same esptool command
pointed at that folder.

`make menuconfig` opens ESP-IDF's configuration UI in the container; the settings that
matter are pinned in `sdkconfig.defaults` so a fresh checkout builds identically.

Why the split: builds, package management and the toolchain live in the container so the
host never drifts from what CI would run.  Docker Desktop on macOS cannot pass a USB device
into a container, so the two steps that touch the port (flash, monitor) run on the host with
the smallest possible tool.

## Simulator (no hardware needed)

`make build-wokwi` builds a variant for the [Wokwi](https://wokwi.com) simulator: UART0
console instead of USB, and the twelve columns driven straight from GPIO instead of through
the decoder.  `wokwi/` holds the diagram (virtual keys, lock buttons, RESTORE, indicator LEDs
on the gate pins, a logic analyzer on the CH446Q lines) and its README explains how to run it.
It uses its own `build-wokwi/` directory and `sdkconfig`, so it never disturbs the hardware
build.  `make sim` runs it headless with the console on your terminal, and `make sim-test`
runs a scripted press of every button and fails if the console does not report each one.

## Layout

| File | What |
|---|---|
| `main/pins.h` | the GPIO plan, identical for the rev 3 board and the devkit rig |
| `main/matrix.c` | 1 kHz scan through the column decoder, 5 ms debounce; `MATRIX_DIRECT_COLUMNS` drives the columns straight from GPIO for the simulator |
| `main/ch446q.c` | CH446Q serial-mode driver: 7 address bits on CS/CK, DAT, STB pulse; RST |
| `main/locks.c` | SHIFT LOCK (left-shift crosspoint held), CAPS LOCK and 40/80 (open-drain gates), state in NVS; RESTORE sense/drive |
| `main/keymap.h` | scanned (row, col) to key legend and host position, bench and rev 3 layouts, generated by `tools/gen_keymap.py` from `layout/switches.json` |
| `main/crosspoint_map.h` | which CH446Q X/Y pin carries each host column/row: in order on the bench rig, routing order on rev 3; generated by `tools/gen_keymap.py` from `pcb/tools/pinmaps.json` |
| `main/led_engine.c` | the LED engine's frame maths: patterns, key actions, lock indicators, brightness, gamma, current cap; no ESP-IDF calls, tested on the host (`test/`) |
| `main/leds.c` | the LED task: a frame every 20 ms, key events from the scan task through a queue, settings in NVS |
| `main/ws2812.c` | SK6812 chain over RMT (10 MHz, GRB, 80 us reset) |
| `main/led_map.h` | which LED sits under each key, where every LED is, the lock keys' LEDs; rev 3 chain and bench strip, generated by `tools/gen_keymap.py` |
| `main/main.c` | tasks: scan/mirror, console |
| `sdkconfig.defaults`, `partitions.csv` | ESP32-S3, 8 MB flash, USB Serial/JTAG console, NVS + app + storage partitions |

## Console

Single characters over the USB console:

| Key | Does |
|---|---|
| `?` | list commands |
| `d` | dump scan-pass time, lock state, RESTORE state and the keys currently down |
| `S` `C` `8` | toggle SHIFT LOCK, CAPS LOCK, 40/80 (saved to NVS; 40/80 applies at the next C128 reset) |
| `R` | press RESTORE for 100 ms through Q3 |
| `r` | RUN/STOP + RESTORE |
| `x` | open every crosspoint, then re-apply SHIFT LOCK |
| `p` `o` | next / previous LED pattern |
| `+` `-` | pattern brightness up / down (1-16) |
| `>` `<` | animation speed up / down (1-10) |
| `a` | next key action |
| `]` `[` | key-action brightness up / down (1-16) |
| `M` `m` | LED current cap +/- 50 mA |
| `N` `n` | LED count +/- 1 (the bench strip, or a shorter test chain) |
| `z` | LED settings back to defaults |
| `l` | show the LED settings and the estimated current |

Every debounced key change is printed as `down Return (1,0)`.  The LED commands stand in
for the SHIFT LOCK command layer (milestone 4) until it exists.

## LED engine

`leds.c` draws a frame every 20 ms and sends it down the SK6812 chain (`PIN_LED_DATA`, through
the 74AHCT1G125 to 5 V).  `led_engine.c` builds each frame in four layers:

1. **Pattern**, at pattern brightness: 0 off, 1 white, 2 Commodore blue, 3 rainbow (across
   the board), 4 rainbow wave, 5 color cycle, 6 breathe, 7 scanner, 8 twinkle, 9 rain,
   10 plasma, 11 VIC-II rows (each key row a VIC-II color, rotating).
2. **Key action**, at key-action brightness: 0 none, 1 flash white, 2 flash color, 3 ripple
   (a ring spreading from the key), 4 cross (the key's row and column), 5 hold (lit while
   held), 6 heat (each press warms the key, blue to red, cooling over seconds).  RESTORE
   lights too, though it isn't in the matrix.
3. **Locks**: the SHIFT LOCK, CAPS LOCK and 40/80 keys' own LEDs light while locked, and
   toggling 40/80 strobes the board green (40 columns) or gray (80), as on the BlingBox.
4. **Gamma and the current cap**: the estimated chain current (about 12 mA per color at full,
   0.6 mA idle per LED) is held under the cap by scaling the whole frame.  The default cap is
   500 mA; full white on all 92 LEDs would be over 3 A.

Defaults: rainbow wave at brightness 6, speed 5, flash white at 12, cap 500 mA.  Settings are
saved to NVS 2 s after the last change.  Patterns use each LED's place on the board
(`led_map.h`), so waves and ripples run across the keyboard, not along the chain.  On the
bench rig the chain is the 60-LED strip from the shopping list, and keys map onto it by
position.

`make test` runs the engine's tests on the host for both boards: dark when off, the cap holds,
flashes fade, hold holds, ripples spread, lock LEDs and the 40/80 strobe, every animated
pattern moves, and nothing freezes after weeks of uptime.

## Matrix conventions

The scanned matrix and the host matrix are different things.  `keymap.h` (generated by
`tools/gen_keymap.py`) gives every scanned (row, column) its legend, `KEY_NAMES`, and what it
does on the C128, `KEY_HOST`: a crosspoint `HOST(row, col)` (host columns 8..10 are the
K0..K2 lines), a lock key, or nothing.  `on_key()` looks the position up and closes the
crosspoint or toggles the lock.

- **Bench rig** (default build): the rev 2.3 board is wired in the C128's own order, 8 x 12,
  so scanned position n is host position n.  Column 11 is where rev 3 used to put the lock
  keys; on the rev 2.3 board they are not scannable, so use the console commands instead.
- **Rev 3** (`make build-rev3`, `BOARD_REV3`): 6 x 20 following the board's key rows and
  columns (`pcb/tools/layout.py` `physical_matrix`), which keeps the matrix copper short.
  The CH446Q's pins are wired in routing order too, so `ch446q_set(row, col)` takes host
  row and column and looks up the chip's pins in `crosspoint_map.h`.
  Columns 0-14 come from the 74HC154, 15-19 straight from GPIO 1, 2, 4, 5 and 6.  The rev 3
  board's pins are picked for the layout (`pcb/tools/gen_sch.py` GPIO), so `main/pins.h` has
  one block for it and one for the bench rig.

RESTORE is not in either matrix.

## The bench rig needs the decoder

`MATRIX_DIRECT_COLUMNS` (one GPIO per column, no decoder) is for the Wokwi build only.  Its
pin list uses the devkit's USB pins (19, 20), strapping pins (3, 45, 46) and, on R8 kits, the
PSRAM bus (35-37): fine in the simulator, but on a real devkit it kills the console or stops
the chip booting, so `matrix.c` refuses to build it with the USB console.  The devkit has no
twelve spare safe pins once the crosspoint, lock and LED lines are taken, so wire the column
decoder (two 74HC138s, or 74LS138s at 5 V; see the bench README).
